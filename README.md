# DXA QC — локальная проверка качества DICOM

Локальная программа контроля качества снимков денситометрии (DXA) по ТЗ ДепЗдрава. Проверяет поясничный отдел позвоночника и проксимальный отдел бедра (правое и левое) по пяти критериям методических рекомендаций и объясняет каждое решение измерениями на снимке.

**Возможности**
- Вход: DICOM, папка или ZIP (в том числе вложенные архивы). Выход: CSV/XLSX по форме ТЗ, строка на файл, плюс вероятность нарушения `quality_prob`.
- Бинарный класс «качественное / есть нарушение» и все причины через «;»: границы сканирования, наклон оси, посторонние предметы, ротация бедра, поля области интереса.
- Дополнительный функционал ТЗ 2.6: серия визуализации (`--overlays`), DICOM SR (`--sr`), коррекция разметки специалистом и веб-интерфейс для пакетной обработки.
- Работает без интернета, на CPU, в контейнере без сети; медицинские изображения никуда не передаются.
- Плохой файл не останавливает пакет: он получает строку Failure с причиной.

**Ограничения**
- Только GE Lunar-подобные снимки позвоночника L1–L4 и проксимального бедра. Другие области отсекаются фильтром вида и получают Failure.
- Метрики получены на 249 размеченных снимках одного источника; на закрытом тесте и другом оборудовании они могут отличаться. Редкие причины (`hip_roi_margins` — 7 случаев, `spine_scan_range` — 6) оценены грубо.
- Программа — помощник специалиста, а не медицинское изделие: решение не заменяет просмотр врачом.

`run.sh` запускает контейнер без сети, только на чтение, с 2 CPU и 4 ГБ памяти. Проверка 19.10: образ из архива на «Для теста.zip» организатора — 3 из 3 Success, повреждённые и не-DICOM файлы получают Failure с причиной, остальной пакет обрабатывается.

Модель выбирается по измеренным результатам, а не по размеру сети. Метрики ниже — оценка на выборке разработки с полностью изолированными фолдами; независимый закрытый тест проводит организатор. ## Быстрый запуск

Из корня проекта с имеющимся окружением и комплектом `models/release/`:

```sh
.venv/bin/dxaqc doctor
.venv/bin/dxaqc --input /path/to/studies --output outputs/result.csv
.venv/bin/dxaqc --input /path/to/studies.zip --output outputs/result.xlsx
```

По умолчанию используются **реальные модели**, CPU, два потока, восемь колонок ТЗ и `quality_prob`. Отсутствующие или повреждённые веса — ошибка запуска. Полезные параметры:

```sh
.venv/bin/dxaqc -i studies.zip -o outputs/detailed.csv --details --scores --fail-on-error
.venv/bin/dxaqc -i studies -o outputs/result.csv --model-dir models/release --device cuda --threads 2
```

`--overlays outputs/overlays.zip` (или папка) сохраняет визуализацию на каждый снимок: PNG и DICOM Secondary Capture отдельной серией того же исследования. На картинке — ось позвоночника с углом, границы L1–L4, окна гребней, рамка ROI с полями в мм, ось шейки и вердикт.

`--sr outputs/sr.zip` (или папка) сохраняет на каждый снимок **DICOM SR** (Basic Text SR, UTF-8). Отчёт кладётся в то же исследование, отдельной серией «DXA QC report (AI)», и ссылается на исходный снимок, поэтому PACS покажет его рядом со снимком. Внутри: анатомическая область, заключение, нарушения теми же текстами, что в CSV, вероятность, измерения (наклон, поля в мм, выступ малого вертела, ось шейки), предупреждения и версия модели. Флаг `UNVERIFIED`: это вывод ИИ, врач его ещё не подписал. UID детерминированы: повторный прогон даёт те же идентификаторы, дублей в PACS не будет.

`--device cuda` требует CUDA-окружения; `--device mps` — доступного Apple MPS. Основной контейнер CPU. `--device auto` выбирает CUDA при наличии, иначе CPU. Тяжёлых обучений запуск CLI не делает.

Рядом создаются `.log` и `.summary.json`: числа Success/Failure, дубликатов, исследований и время. При `--details` предупреждение `review:` означает необходимость проверки результата человеком; бинарный класс остаётся 0/1 по ТЗ. Это предупреждение, а не валидированный третий класс.

## Веб-интерфейс

```sh
.venv/bin/dxaqc serve --port 8080          # затем открыть http://127.0.0.1:8080/ (новый интерфейс — /journal/)
./scripts/run-ui.sh                        # то же в контейнере; порт опубликован только на 127.0.0.1
```

Перетащите ZIP, папку или файлы DICOM. Строки появляются по мере анализа, каждый готовый снимок «проявляется» в списке. Справа — снимок с разметкой: уровни L1–L4, ось с наклоном в градусах, поля кадра в мм, рамка ROI бедра, ось шейки и малый вертел. Найденные посторонние предметы обведены рамкой с подписью «Металл» или «Проволока». Нарушенный критерий выделен красным и стоит первым. Счётчики «Норма / Брак / Ошибки» в шапке работают как фильтр списка. Шторка «Сравнить со снимком» или клавиша `M` сравнивает разметку с исходным снимком, `↑`/`↓` листают снимки, `E` — исправить разметку, `Enter` — подтвердить. Меню «Отчёт» скачивает отчёт CSV/XLSX в формате ТЗ (8 колонок + `quality_prob`) и архив DICOM SR. Адрес `#job=…` переживает перезагрузку страницы.

**Коррекция разметки врачом (ТЗ 2.6).** «Подтвердить брак» или «Подтвердить норму» — врач согласен с моделью. «Исправить» — на снимке появляются точки-ориентиры (границы L1–L4, края рамки ROI, ось шейки). Их можно перетаскивать мышью или пальцем, либо сдвигать стрелками (с Shift — по 5 px). Измерения меняются сразу, а когда точку отпускают, модель пересчитывает все критерии по новым точкам; малый вертел находится заново. На карточке каждого критерия врач может поставить «Нарушение» или «Норма» вопреки модели. Подтверждённое решение заменяет решение модели в отчёте. В SR такой снимок получает флаг `VERIFIED` и новый SOP Instance UID, а заключение модели сохраняется отдельной строкой, чтобы изменение можно было отследить. Кнопка «Исправления» выгружает JSON с точками и решениями модели и врача: это готовая экспертная разметка для дообучения.

Интерфейс работает без интернета: шрифты (Golos Text, Fira Sans Condensed) и код лежат в пакете (`src/dxaqc/webui_dist`), браузер обращается только к локальному серверу. Загруженные исследования хранятся во временной папке и удаляются при остановке сервера. Исходники — в `ui/` (React + Vite); пересборка: `cd ui && bun install && bun run build`.

Интерфейсов два, оба на одном сервере и одном API. Классический («Негатоскоп», тёмный) — на `/`, исходники в `ui/`. Новый «Журнал контроля качества» — на `/journal/`, исходники в `ui-journal/`, сборка в `src/dxaqc/webui_journal_dist`: на главном экране изометрический денситометр сканирует фантом позвоночника и показывает, как система меряет критерии ТЗ, ниже — результаты проверки на 249 снимках (одна отметка — один снимок); в рабочем месте — контрольный листок пакета «критерии × снимки». Дизайн-система — `ui-journal/DESIGN.md`. Пересборка: `cd ui-journal && bun install && bun run build`.

GPU не нужен: весь инференс идёт на CPU. Замер: 40 снимков из обучающего архива (позвоночник и бедро), все Success, Apple M4 Pro, CPU:

Под эмуляцией x86 на Apple Silicon время в десятки раз больше и показателем не является.

## Установка и контейнер

Исследовательское окружение закреплено в `uv.lock`:

```sh
uv sync --frozen
# Только при восстановлении из локальных результатов обучения:
.venv/bin/python scripts/prepare_release.py
```

**Веса моделей** (622 МБ) в Git не хранятся: файлы CNN бедра больше лимита GitHub в 100 МБ. Для запуска достаточно готового образа с [Яндекс Диска][disk] — веса в нём. Для сборки из исходников возьмите там же архив весов `dxaqc-models-2026-09-19.zip`; распакуйте его так, чтобы получилось `models/release/manifest.json`, и проверьте целостность:

```sh
unzip dxaqc-models-2026-09-19.zip && mv dxaqc-models-2026-09-19 models/release
.venv/bin/dxaqc doctor --model-dir models/release      # SHA-256 каждого файла по manifest.json
(cd models/release && sha256sum -c SHA256SUMS)          # то же стандартной утилитой (macOS: shasum -a 256 -c)
```

Git хранит исходники и отчёты, большие веса находятся в отдельном комплекте. `prepare_release.py` копирует только завершённые выбранные фолды и проверяет SHA-256. Из одного клона Git без весов инференс не заработает; используйте комплект поставки или воспроизведите обучение.

```sh
./scripts/build.sh
./scripts/run.sh /absolute/studies.zip /absolute/results/result.csv
./scripts/smoke_image.sh "$PWD/test.zip" 0.8904 0.9945 0.9861     # проверка образа: --version, doctor, страницы и favicon, API, CSV/XLSX/SR без сети
```

Числа в `smoke_image.sh` — эталонные `quality_prob` трёх снимков из тестового архива организатора («Для теста»); без них скрипт проверяет всё, кроме совпадения вероятностей.

Сборка скачивает закреплённые зависимости. Запуск контейнера использует `--network none`, два CPU, read-only filesystem и временную папку; данные не отправляются в сеть. Linux x86_64 для сдачи: `./scripts/build.sh --platform linux/amd64`; если на целевой машине нет интернета для сборки, есть готовый образ на [Яндекс Диске][disk]: `docker load -i dxaqc_amd64.tar.gz`. Для Docker context без доступа к папкам хоста доступен проверенный `scripts/run-copy.sh` (выходное имя должно быть новым). Подробности — [развёртывание](docs/DEPLOYMENT.md).

## Формат результата

Значения и колонки — по ответам организатора на вопросы участников (6, 8, 15):

```text
path_to_study,study_uid,image_uid,anatomical_region,quality_class,violation_type,processing_status,time_of_processing,quality_prob
Для теста/CR000000_ПОП.dcm,…,Поясничный отдел позвоночника,1,Присутствуют посторонние предметы,Success,0.8784,0.8904
Для теста/CR000000_ППОБ.dcm,…,Проксимальный отдел бедра,1,Некорректная укладка,Success,5.885,0.9945
```

- `anatomical_region`: «Поясничный отдел позвоночника» или «Проксимальный отдел бедра» (сторона не выводится).
- `quality_class`: **0 — качественное**, **1 — обнаружено нарушение**; пусто при Failure.
- `violation_type` — закрытый список организатора, несколько значений через `;`, пусто при отсутствии нарушений:
  - позвоночник: «Некорректная укладка» (границы сканирования), «Не выровнена ось позвоночника», «Присутствуют посторонние предметы»;
  - бедро: «Некорректная укладка» (ротация), «Некорректная область интереса».
- Если бинарная модель видит брак, а ни одна причина не достигла своего порога, ставится причина, ближе всего подошедшая к порогу; в `--details` это помечено как `review: … reported the closest one`, в интерфейсе — «причина выведена». На изолированной валидации (до правила рамки ROI) так переназначено 11 браков бедра: F1 ротации 0.595 → 0.612, F1 качества не меняется.
- `processing_status`: `Success` или `Failure`. `Success` означает завершённую обработку, не высокую достоверность заключения.
- `time_of_processing`: секунды; включает загрузку нужной модели при первом обращении.
- `quality_prob` — вероятность нарушения в [0; 1] для ROC-AUC. У позвоночника и бедра свои шкалы и пороги; каждая приведена так, что порог решения ровно 0.5: порядок внутри области сохраняется, `quality_prob ≥ 0.5` тогда и только тогда, когда `quality_class = 1`. Если врач в интерфейсе изменил вердикт, вероятность становится 1 или 0.

Внутри сервиса (API, интерфейс, JSON) используются коды `lumbar_spine`/`hip_left`/`hip_right` и `spine_scan_range`, `spine_axis_tilt`, `spine_artifact`, `hip_positioning`, `hip_roi_margins`; в тексты организатора они переводятся только при записи CSV/XLSX.

`--type-probs` добавляет `prob_<код>` — вероятность каждого типа нарушения в шкале `quality_prob` (0.5 — порог этой причины, ≥ 0.5 тогда и только тогда, когда код есть в `violation_type`; колонки другой области пустые); по ним ROC-AUC считается отдельно для каждого типа. `--scores` добавляет непрерывные оценки; они не являются доказанно откалиброванной вероятностью. `--details` добавляет `error_message`; `--strict-columns` оставляет колонки ТЗ и `quality_prob`. Повреждённый DICOM даёт Failure, остальные файлы продолжают обрабатываться. Одинаковые пиксели вычисляются один раз, все входные файлы сохраняют отдельные строки.

Коды завершения: `0` — отчёт записан (может содержать Failure), `2` — ошибка конфигурации/пакета, `3` — Failure при `--fail-on-error`, `4` — пустой вход, `130` — прерывание пользователем.

## Как это работает

Снимок проходит три шага: **какая это область** → **измерения по анатомическим ориентирам** → **решение по каждой причине из ТЗ**. Брак выставляется, когда найдена хотя бы одна причина; причины перечисляются в `violation_type`.

| Шаг | Что делает | Как устроено |
|---|---|---|
| Область и вид | позвоночник / правое / левое бедро; снимки вне задачи не получают вердикт | замороженный DenseNet121 + линейная голова; отдельный фильтр вида по признакам ориентиров |
| Масштаб | мм на пиксель | 0.6 мм, квадратный пиксель (обоснование ниже) |
| Ориентиры | L1–L4, гребни подвздошных костей, рамка ROI бедра, ось шейки | ConvNeXt-Tiny + FPN, тепловые карты; обучен на линиях автоматической разметки GE Lunar из внешнего набора Arak как на слабых метках |
| `spine_axis_tilt` | наклон оси L1→L4, градусы (порог ТЗ 5°) | измерение по ориентирам, калибровка наклона 0.921 по известным поворотам |
| `spine_scan_range` | видны ли верхние края гребней и половина Th12 | поля кадра и окна гребней по ориентирам |
| `spine_artifact` | проволока, металл | детектор хребтов (гессиан) и насыщения по ориентирам + CNN-скор |
| `hip_positioning` | ротация: малый вертел «слегка выступает» (рис. 5 ТЗ) | детерминированный детектор малого вертела по медиальному контуру + дообученный ConvNeXt-Tiny 384 |
| `hip_roi_margins` | 3 см сверху/снизу, 2 см сбоку (рис. 6 ТЗ) | правило: рамка ROI по ориентирам выходит за край снимка (на практике — за нижний или правый край, где сеть ориентиров достраивает точку за кадром) → нарушение и брак (с 18.10, заменило голову ConvNeXt; [обоснование](docs/METRICS_BY_TYPE.md#что-дало-каждое-правило)) |

**Масштаб.** Организатор сообщил размер пикселя сканера 0,6 мм по X и 1,05 мм по Y (ответ на вопрос 1). В выгруженных DICOM пиксель, по всем признакам, квадратный, около 0,6 мм: при 0,6 мм длина L1–L4 — 137 мм (норма у взрослых 130–160), при 1,05 мм было бы 240 мм; головка бедра на снимках круглая, а не сплющенная. Разметка экспертов это подтверждает: правило ТЗ «наклон > 5°» совпадает с ней в квадратных пикселях (F1 0.55) и не совпадает в масштабе 1,05 мм (F1 0.00 — ни одного снимка выше 5° при 10 помеченных). Вероятно, 1,05 мм — шаг строк при сканировании до пересчёта изображения. Тег `ExposedArea` одинаков у кадров разного размера ([180, 192]) и масштаба не несёт. На решения модели масштаб не влияет: она обучена на тех же пикселях; он влияет только на показанные миллиметры.

Детекторы малого вертела и артефактов не обучаются на метках качества. Они построены по критериям ТЗ и заморожены после визуальной проверки со скрытыми метками. `--overlays` рисует все измерения на снимке и сохраняет их отдельной DICOM-серией.

## Устойчивость и эксплуатация

- **Данные организатора:** 499/499 DICOM из `НД_для_обучения.zip` — Success; `разметка.xlsx` внутри архива пропускается как документ. Кириллица в именах ZIP (cp866) раскодируется. Около 9 с на исследование на CPU при 2 потоках — при лимите ТЗ 3 мин.
- **Плохой вход не останавливает пакет:** вложенные ZIP, пути `\` из Windows, повторные имена, обрезанные, пустые и не-DICOM файлы дают строку Failure с причиной или пропускаются, отчёт пишется всегда (подробно — [развёртывание](docs/DEPLOYMENT.md)).
- **Воспроизводимость:** два прогона на 305 снимках дают одинаковый CSV (кроме времени).
- **Платформа:** образ `linux/amd64` для машины организатора даёт те же решения, что и локальный прогон; готовый образ архивом для установки без интернета — на [Яндекс Диске][disk].
- **Сдвиги данных:** при поворотах, сдвигах и изменении контраста наклон оси дрейфует не более чем на 0.9°, меняется 1–5% решений. Масштаб из DICOM уменьшает ошибку миллиметровых измерений в 11 раз. Снимки вне задачи (не позвоночник и не бедро) отсекаются фильтром вида.

## Известные ошибки и их обработка

| Ситуация | Что происходит | Что делать |
|---|---|---|
| Файл не DICOM, пустой, обрезанный, без PixelData | строка `Failure` с причиной в `error_message` (`--details`); пакет продолжается | проверить выгрузку из PACS |
| Документы рядом со снимками (`.xlsx`, `.pdf`, `.png` …), `DICOMDIR`, `__MACOSX` | пропускаются, считаются в `skipped_non_dicom` сводки | — |
| Однотонный кадр | `Failure`: «пустой кадр: изображение константное» | снимок не содержит изображения |
| Снимок не позвоночника и не бедра | `Failure` с оценкой фильтра вида | область вне задачи |
| Многокадровый DICOM | берётся первый кадр, предупреждение в `error_message` | проверить вручную |
| Нет StudyInstanceUID / SOPInstanceUID | детерминированный UID `2.25.*` по пикселям и папке | — |
| Небезопасный элемент ZIP (`../`, абсолютный путь, symlink, шифрование, > 512 MiB) | не извлекается, строка `Failure` | — |
| Признаки zip-бомбы (> 200 000 файлов или > 64 GiB) или нет места | пакет отклоняется, код выхода 2 | увеличить временную папку или разбить архив |
| Нет весов или SHA-256 не совпадает | ошибка запуска, код 2; `dxaqc doctor` покажет файл | восстановить комплект `models/release` |
| Выход модели нарушает контракт отчёта (NaN, неверный код) | строка превращается в `Failure`, отчёт пишется | сообщить разработчикам |
| Брак без причины выше порога | ставится ближайшая к порогу причина, `review:` в `error_message` | проверить снимок специалистом |
| Масштаб пикселя в DICOM отсутствует | 0,6 мм/px; на решения не влияет, только на миллиметры | — |
| Сбой записи SR или наложения | строка отчёта не страдает; счётчики `sr_failures`, `overlay_failures` в сводке | см. `.log` |
| Прерывание (Ctrl+C) | код 130, частичный отчёт не пишется | перезапустить |

Любое необработанное исключение внутри файла ловится и записывается в его строку; программа не падает на отдельных файлах. Подробности — [развёртывание](docs/DEPLOYMENT.md).

## Эксперименты

Каждая гипотеза проверялась одним протоколом: те же фолды по исследованиям, парный bootstrap по исследованиям, принятие только если 95% ДИ прироста целиком выше нуля. С 20.09 гипотеза фиксировалась в коммите до первого запуска; с октября при нескольких вариантах сразу интервал поправляется по Бонферрони.

| Направление | Что проверяли | Результат | Решение |

| Самообучение | DINO на 4.1 тыс. внешних DXA, DINOv2-S | AUC бедра 0.574 против 0.627 | отклонено |

**Вывод.** Ручная геометрия, дообученная CNN и замороженный RAD-DINO дают на ротации бедра одинаковые 0.83–0.86 AUC, а пропущенные нарушения не отличаются от нормы ни по одному измеримому критерию ТЗ и методички организатора. Остаток ошибок, вероятнее всего, — вариативность экспертной разметки. Проверить это можно только повторной разметкой экспертами.

from dxaqc.api import create_predictor, analyze
predictor = create_predictor('models/release', threads=2)
