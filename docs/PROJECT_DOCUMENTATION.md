# DXA QC — документация

DXA QC — локальная система контроля качества DICOM-снимков двухэнергетической рентгеновской абсорбциометрии (DXA). Она анализирует поясничный отдел позвоночника и проксимальные отделы правого и левого бедра, определяет наличие нарушений и показывает измерения, на которых основано решение.

Все команды ниже выполняются из корня репозитория в POSIX-оболочке. Основной вариант поставки для машины организатора — Docker-образ для Linux x86_64.

## 1. Назначение и возможности

Система разработана для автоматизированной проверки снимков по критериям технического задания ДепЗдрава. Для каждого изображения она возвращает бинарный класс качества, список обнаруженных причин нарушения и показатель `quality_prob`.

Поддерживаются пять типов нарушений:

| Анатомическая область | Проверяемый критерий |
|---|---|
| Поясничный отдел позвоночника | Границы сканирования |
| Поясничный отдел позвоночника | Выравнивание оси позвоночника |
| Поясничный отдел позвоночника | Наличие посторонних предметов |
| Проксимальный отдел бедра | Укладка и ротация бедра |
| Проксимальный отдел бедра | Поля области интереса, ROI |

Программа принимает отдельные DICOM-файлы, папки с исследованиями и ZIP-архивы, включая поддерживаемые вложенные архивы. Основной результат — CSV или XLSX по форме технического задания. Дополнительно формируются визуализации, DICOM Secondary Capture и структурированные отчёты DICOM SR.

С системой можно работать через командную строку, локальный веб-интерфейс, Python API и HTTP API. Специалист может исправлять анатомические ориентиры и решения модели, подтверждать заключение и выгружать исправления для последующего дообучения.

Инференс выполняется на локальной машине и не требует обращения к внешним сервисам. Для основной поставки достаточно CPU. Ошибка отдельного снимка отражается в отчёте и не прекращает обработку остальных файлов.

## 2. Архитектура и структура проекта

### 2.1. Общая схема

Вычислительное ядро отделено от способов взаимодействия с пользователем. CLI, HTTP-сервер и веб-интерфейс используют общие компоненты чтения DICOM, анализа снимков и подготовки результатов. Это позволяет применять одну логику модели в интерактивном и пакетном сценариях.

~~~mermaid
flowchart TD
    A["CLI / Python API"] --> C["Пакетная обработка"]
    B["Веб-интерфейс / HTTP API"] --> C
    C --> D["Чтение DICOM и распаковка ZIP"]
    D --> E["Определение области и вида"]
    E --> F["Поиск анатомических ориентиров"]
    F --> G["Измерения, детекторы и модели качества"]
    G --> H["Вердикт и причины нарушения"]
    H --> I["CSV / XLSX и сводка"]
    H --> J["Визуализации и DICOM SR"]
    H --> K["Просмотр и коррекция специалистом"]
~~~

Пакетная обработка включает подготовку входа, анализ каждого файла, проверку контракта отчёта и возврат строк со статистикой. Формирование выходных файлов выполняется соответствующими компонентами CLI и веб-сервиса.

## 3. Алгоритм анализа и критерии качества

### 3.1. Подготовка изображения

DICOM читается средствами pydicom и pylibjpeg. При подготовке учитываются slope/intercept, выполняется инверсия MONOCHROME1 и нормализация изображения в uint8. Постоянный по яркости кадр получает статус `Failure`.

Для многокадрового файла анализируется первый кадр с предупреждением. Цветные данные переводятся в среднее по каналам; перенос качества модели на цветные отчёты не валидирован.

### 3.2. Область и анатомические ориентиры

Сначала определяется область: `lumbar_spine`, `hip_left` или `hip_right`. Для этого используются замороженный DenseNet121 и линейная голова. Дополнительный фильтр вида по признакам ориентиров отсекает изображения вне поддерживаемой задачи.

Сеть ConvNeXt-Tiny с FPN предсказывает тепловые карты ориентиров: уровни L1–L4, гребни подвздошных костей, рамку ROI бедра и ось шейки. При обучении ориентиров использованы линии автоматической разметки GE Lunar из внешнего набора Arak как слабые метки анатомии.

### 3.3. Проверка критериев

| Внутренний код | Способ проверки |
|---|---|
| `spine_scan_range` | Оцениваются границы кадра и положение анатомических ориентиров, связанных с охватом позвоночника и подвздошных гребней |
| `spine_axis_tilt` | По ориентирам L1–L4 вычисляется наклон оси; измерение откалибровано по известным поворотам |
| `spine_artifact` | Объединяются детекторы хребтов и насыщения, геометрия ориентиров и CNN-оценка |
| `hip_positioning` | Используются детектор малого вертела по медиальному контуру и дообученная ConvNeXt-Tiny с входом 384 px |
| `hip_roi_margins` | В логике релиза с 18 октября 2026 года нарушение фиксируется, когда предсказанная рамка ROI выходит за край снимка |

В техническом задании фигурируют наклон 5° и поля ROI 3 см сверху/снизу и 2 см сбоку. Выбранная система сочетает измерения с обученными оценками и правилами релиза. Результаты экспериментов с буквальным применением этих порогов приведены в [README](../README.md); они не дали улучшения общей классификации.

Детекторы малого вертела и артефактов построены по критериям задачи и не обучаются непосредственно на метках качества.

### 3.4. Итоговое решение и объяснение

В отчёте используются два класса: `0` — качественный снимок, `1` — обнаружено нарушение. Для нарушения указывается одна или несколько причин. Если бинарная модель обнаружила брак, но отдельные причины не достигли своих порогов, система выбирает причину, ближайшую к порогу. В подробном отчёте это сопровождается предупреждением `review:`.

Показатель `quality_prob` лежит в диапазоне от 0 до 1 и приведён к порогу 0,5 отдельно для позвоночника и бедра. При автоматическом решении `quality_prob >= 0.5` соответствует классу `1`. Непрерывные оценки, добавляемые параметром `--scores`, не следует считать доказанно откалиброванными вероятностями.

Для объяснения результата отображаются ось и угол наклона позвоночника, уровни L1–L4, рамка ROI и её поля, ось шейки, малый вертел и области найденных артефактов. Миллиметровые измерения зависят от корректности масштаба изображения. В документации релиза для исходной выгрузки обосновано приближение квадратного пикселя около 0,6 мм; при отсутствии масштаба используется 0,6 мм/px. Этот вопрос требует проверки при переносе на другое оборудование.

## 5. Системные требования

| Ресурс | Минимальная конфигурация | Рекомендуемая конфигурация |
|---|---|---|
| CPU | 1 ядро x86_64 с AVX2 или arm64 | 4 ядра |
| RAM | 2 ГБ | 4 ГБ |
| GPU | Не требуется | Основной поставляемый контейнер использует CPU |
| Диск | Около 5 ГБ с учётом образа и временных данных | 10 ГБ и дополнительное место для больших пакетов |
| ОС для поставки | Linux x86_64, Docker 20+ | Та же платформа |
| Локальный запуск из исходников | Linux или macOS, Python 3.12 | Закреплённое окружение через uv |

Скрипт пакетного запуска ограничивает контейнер двумя CPU и 4 ГБ RAM, выделяет 3 ГБ временного пространства в `/tmp`. Большие архивы могут потребовать изменения этих лимитов.

CLI поддерживает `--device cpu`, `cuda`, `mps` и `auto`. Для CUDA или Apple MPS необходимо подходящее окружение. Режим `auto` выбирает CUDA при наличии и CPU в остальных случаях. Количество потоков задаётся через `--threads`, допустимы значения от 1 до 8; значение по умолчанию — 2.

Архитектура контейнера должна соответствовать целевой машине. Для Linux x86_64 образ собирается с `--platform linux/amd64`. Время исполнения x86_64 под эмуляцией на Apple Silicon не характеризует скорость на целевой x86_64-машине.

## 6. Комплект поставки

Исходный код, скрипты, закреплённые зависимости и документация хранятся в Git-репозитории. Крупные материалы передаются отдельным комплектом на Яндекс Диске:

| Артефакт | Назначение |
|---|---|
| `dxaqc_amd64.tar.gz` | Готовый Docker-образ Linux x86_64 с зависимостями и выбранными весами |
| `SHA256-образ.txt` | Контрольная сумма архива контейнера |
| `dxaqc-models-2026-09-19.zip` | Архив весов для сборки и запуска из исходников; размер пересобранного архива — 621 МБ |
| Видеодемонстрация | Загрузка пакета, анализ, отчёт и коррекция специалистом |
| Презентация и заметки докладчика | Материалы представления решения на Яндекс Диске |

Для пересобранного архива `dxaqc-models-2026-09-19.zip` ожидается SHA-256:

~~~text
a235e8234fc435bfc1e1bbc0bd6ce5a46a614fd2dd759d75c318b78182a20288
~~~

Контрольная сумма должна соответствовать фактически полученному архиву. После распаковки проверяются также отдельные файлы модели по `manifest.json` и `SHA256SUMS`.

Исходные DICOM организатора и обучающие изображения в релиз не включаются. Презентация и иллюстрации из прежнего каталога `docs/presentation/` в текущем дереве репозитория отсутствуют; материалы презентации передаются отдельно.

## 7. Развёртывание и проверка установки

### 7.1. Запуск готового образа

Этот вариант позволяет работать на целевой машине без скачивания Python-зависимостей и весов. Нужны исходные скрипты репозитория, установленный Docker и комплект поставки.

1. Сравните SHA-256 архива образа со значением в сопроводительном файле:

~~~sh
sha256sum dxaqc_amd64.tar.gz
~~~

2. Загрузите образ:

~~~sh
docker load -i dxaqc_amd64.tar.gz
~~~

Для комплекта, описанного в README, используется тег `dxaqc:local`. Если Docker сообщает другой тег, передайте его скриптам через переменную `DXAQC_IMAGE`.

3. Запустите пакетную обработку:

~~~sh
./scripts/run.sh /absolute/studies.zip /absolute/results/result.csv
~~~

Входной путь может указывать на файл, каталог или ZIP. Вход монтируется только для чтения; результаты записываются в каталог, соответствующий выходному пути. Скрипт использует `--network none`, read-only корневую файловую систему и временную папку.

4. При необходимости запустите веб-интерфейс:

~~~sh
./scripts/run-ui.sh
~~~

Откройте [http://127.0.0.1:8080/journal/](http://127.0.0.1:8080/journal/). Классический интерфейс доступен по [http://127.0.0.1:8080/](http://127.0.0.1:8080/).

Веб-контейнер публикует порт только на loopback-адресе хоста. Его запуск отличается от пакетного сценария: браузер обращается к локальному HTTP-серверу. Для интерфейса не требуется доступ к внешним ресурсам.

### 7.2. Подготовка исходников и весов

Из корня репозитория установите закреплённое окружение:

~~~sh
uv sync --frozen
~~~

Проверьте архив весов и распакуйте его так, чтобы получился путь `models/release/manifest.json`:

~~~sh
sha256sum dxaqc-models-2026-09-19.zip
mkdir -p models
unzip dxaqc-models-2026-09-19.zip
mv dxaqc-models-2026-09-19 models/release
~~~

Пример рассчитан на комплект, содержащий каталог `dxaqc-models-2026-09-19`, и первоначальную установку без существующего `models/release/`.

Проверьте структуру и целостность:

~~~sh
.venv/bin/dxaqc doctor --model-dir models/release
(cd models/release && sha256sum -c SHA256SUMS)
~~~

На macOS вместо `sha256sum` можно использовать `shasum -a 256`.

Команда `doctor` проверяет состав модели и SHA-256; она не выполняет полный анализ снимка и не оценивает качество предсказания. Если комплект отсутствует или повреждён, запуск модели завершается ошибкой. Один клон репозитория без весов не позволяет выполнить инференс.

Скрипт `scripts/prepare_release.py` предназначен для восстановления комплекта из завершённых локальных результатов обучения. Для обычной установки используйте поставляемые веса.

### 7.3. Сборка контейнера из исходников

После размещения весов выполните:

~~~sh
./scripts/build.sh --platform linux/amd64
./scripts/run.sh /absolute/studies.zip /absolute/results/result.xlsx
~~~

Сборка требует доступа к базовому образу и индексам закреплённых Python-пакетов. После сборки пакетная обработка выполняется с отключённой сетью.

Для Docker context, в котором не работают bind mounts к файлам хоста, предусмотрен вариант с копированием:

~~~sh
./scripts/run-copy.sh /absolute/studies.zip /absolute/results/new-result.xlsx
~~~

Выходное имя в этом сценарии должно быть новым. Скрипт создаёт отдельный контейнер, копирует вход, возвращает отчёт, лог и сводку, затем удаляет контейнер. Подробности — в [DEPLOYMENT.md](DEPLOYMENT.md).

### 7.4. Проверка работоспособности

Проверьте версию, веса и обработку доступного тестового пакета:

~~~sh
.venv/bin/dxaqc --version
.venv/bin/dxaqc doctor
.venv/bin/dxaqc -i /absolute/studies.zip -o outputs/result.csv --details
~~~

Для контейнера предусмотрена проверка версии, весов, страниц, API и экспортов:

~~~sh
./scripts/smoke_image.sh /absolute/test.zip
~~~

Дополнительные аргументы эталонных вероятностей в этом скрипте используются только с теми снимками, для которых они были измерены. Сам факт записи отчёта следует проверять вместе со статусами строк и сводкой.

<a id="cli"></a>

## 8. Пакетная обработка через CLI

При запуске из подготовленного окружения:

~~~sh
.venv/bin/dxaqc --input /path/to/studies --output outputs/result.csv
.venv/bin/dxaqc --input /path/to/studies.zip --output outputs/result.xlsx
~~~

Формат отчёта выбирается по расширению выходного файла. По умолчанию используется модель релиза, CPU и два потока.

Для получения подробного отчёта, визуализаций и DICOM SR:

~~~sh
.venv/bin/dxaqc   -i /path/to/studies.zip   -o outputs/result.xlsx   --details   --overlays outputs/overlays.zip   --sr outputs/sr.zip
~~~

| Параметр | Назначение |
|---|---|
| `--model-dir` | Папка с `manifest.json` и весами |
| `--device` | Устройство исполнения: `cpu`, `cuda`, `mps` или `auto` |
| `--threads` | Количество потоков CPU |
| `--details` | Добавление `error_message` и предупреждений |
| `--scores` | Добавление непрерывных оценок для анализа |
| `--type-probs` | Добавление вероятностных оценок отдельных причин |
| `--strict-columns` | Восемь колонок ТЗ и `quality_prob` |
| `--fail-on-error` | Код завершения 3 при наличии хотя бы одной строки `Failure`; отчёт сохраняется |
| `--overlays` | Каталог или ZIP с PNG и DICOM Secondary Capture |
| `--sr` | Каталог или ZIP с DICOM SR |
| `--path-mode dir` | Указание пути исследования вместо пути отдельного файла |

Рядом с отчётом создаются лог и файл `.summary.json`. Сводка содержит количество успешных и ошибочных обработок, сведения о дубликатах, исследованиях и времени работы.

<a id="results"></a>

## 9. Формат результатов

### 9.1. CSV и XLSX

Основной отчёт содержит восемь колонок технического задания и дополнительную колонку `quality_prob`:

~~~text
path_to_study,study_uid,image_uid,anatomical_region,quality_class,violation_type,processing_status,time_of_processing,quality_prob
~~~

| Поле | Содержание |
|---|---|
| `path_to_study` | Путь к снимку или исследованию с учётом выбранного режима |
| `study_uid` | Идентификатор исследования |
| `image_uid` | Идентификатор изображения |
| `anatomical_region` | «Поясничный отдел позвоночника» или «Проксимальный отдел бедра» |
| `quality_class` | `0` — качественное; `1` — обнаружено нарушение; пустое значение при `Failure` |
| `violation_type` | Формулировки организатора; несколько причин разделяются `;` |
| `processing_status` | `Success` или `Failure` |
| `time_of_processing` | Время в секундах; при первом обращении включает загрузку нужной модели |
| `quality_prob` | Показатель вероятности нарушения от 0 до 1 с порогом решения 0,5 |

В CSV/XLSX сторона бедра отдельно не выводится. Внутри Python API, HTTP API и интерфейса используются коды областей `lumbar_spine`, `hip_left`, `hip_right` и коды причин. Перевод в русские формулировки выполняется при записи табличного отчёта.

Соответствие кодов и текстов:

| Код | Формулировка в отчёте |
|---|---|
| `spine_scan_range` | Некорректная укладка |
| `spine_axis_tilt` | Не выровнена ось позвоночника |
| `spine_artifact` | Присутствуют посторонние предметы |
| `hip_positioning` | Некорректная укладка |
| `hip_roi_margins` | Некорректная область интереса |

Статус `Success` означает, что обработка завершилась. Он не является показателем уверенности модели или отсутствия нарушений.

Параметр `--type-probs` добавляет поля `prob_<код>`; для причин другой анатомической области значения остаются пустыми. Одинаковые пиксели обрабатываются один раз, при этом каждому входному файлу сохраняется отдельная строка.

### 9.2. Визуализации и DICOM SR

Визуализации включают измерения и анатомические ориентиры. DICOM Secondary Capture сохраняется отдельной серией того же исследования.

DICOM SR формируется как Basic Text SR в UTF-8, ссылается на исходный снимок и содержит область, заключение, нарушения, вероятность, измерения, предупреждения и версию модели. Первоначальный отчёт имеет флаг `UNVERIFIED`.

После подтверждения специалистом отчёт получает `VERIFIED` и новый SOP Instance UID. Исходное заключение модели сохраняется отдельно, что позволяет проследить внесённое изменение.

## 10. Веб-интерфейс и проверка специалистом

Для локального запуска из исходников:

~~~sh
.venv/bin/dxaqc serve --model-dir models/release --port 8080
~~~

Сервер предоставляет два интерфейса:

| Адрес | Интерфейс | Исходники |
|---|---|---|
| `/` | Классический «Негатоскоп» | [ui](../ui) |
| `/journal/` | «Журнал контроля качества» | [ui-journal](../ui-journal) |

Оба интерфейса работают с одним сервером и общей логикой анализа. Основной сценарий:

1. Загрузить ZIP, папку или отдельные DICOM.
2. Дождаться появления строк результатов по мере анализа.
3. Выбрать снимок и просмотреть ориентиры, измерения и причины нарушения.
4. При необходимости исправить точки и решения отдельных критериев.
5. Подтвердить заключение.
6. Скачать CSV/XLSX, DICOM SR и JSON исправлений.

В классическом интерфейсе предусмотрены сравнение с исходным изображением, фильтры «Норма / Брак / Ошибки» и горячие клавиши: `M` — сравнение, стрелки — переход между снимками, `E` — коррекция, `Enter` — подтверждение.

При перемещении ориентиров измерения обновляются, а после завершения перемещения пересчитываются критерии. Специалист может изменить решение по отдельной причине. Подтверждённый вердикт используется в экспортируемом отчёте; `quality_prob` для изменённого врачом решения становится 0 или 1. Такие значения отражают экспертную коррекцию, а не новую оценку уверенности модели.

Выгрузка «Исправления» содержит точки и решения модели и специалиста. Она предназначена для подготовки экспертной разметки; автоматического дообучения во время пользовательской работы не выполняется.

Данные загруженных исследований хранятся во временной папке сервера и удаляются при его остановке. Подробные действия описаны в [USER_GUIDE.md](USER_GUIDE.md), дизайн интерфейса «Журнал» — в [DESIGN.md](../ui-journal/DESIGN.md).

Пересборка интерфейсов при изменении исходников:

~~~sh
cd ui
bun install
bun run build
~~~

Для второго интерфейса аналогичные команды выполняются из каталога `ui-journal/`.

<a id="api"></a>

## 11. Программные интерфейсы

### 11.1. Python API

Публичные функции находятся в `dxaqc.api`:

~~~python
from dxaqc.api import analyze, create_predictor

predictor = create_predictor(
    model_dir="models/release",
    device="cpu",
    threads=2,
)

rows, summary = analyze(
    "studies.zip",
    predictor=predictor,
)
~~~

`create_predictor` создаёт модель с указанными весами, устройством и количеством потоков. Один экземпляр предиктора можно использовать для нескольких вызовов, чтобы не повторять загрузку модели.

`analyze` возвращает список словарей строк и словарь статистики. Ошибки отдельных файлов возвращаются в строках. Ошибки конфигурации или подготовки пакета могут приводить к исключению.

В сводке используются статусы `empty`, `partial_failure` и `complete`; также возвращаются сведения о предикторе, `model_id` и времени. Детали сигнатур — в [api.py](../src/dxaqc/api.py).

### 11.2. HTTP API пакетной обработки

Запуск:

~~~sh
.venv/bin/dxaqc serve   --model-dir models/release   --host 127.0.0.1   --port 8080   --threads 2
~~~

Проверка готовности:

~~~sh
curl http://127.0.0.1:8080/health
~~~

Ответ содержит `status` со значением `ok` и идентификатор `model_id`.

Отправка архива:

~~~sh
curl   -H 'Content-Type: application/zip'   --data-binary @studies.zip   http://127.0.0.1:8080/v1/batch   > response.json
~~~

| Свойство | Значение |
|---|---|
| Метод и адрес | `POST /v1/batch` |
| Тело запроса | Бинарное содержимое ZIP |
| Тип содержимого | `application/zip` |
| Размер | От 1 байта до 512 MiB, 536 870 912 байт |
| Заголовок длины | Требуется корректный `Content-Length`; curl формирует его при отправке файла |
| Ответ | JSON с массивом `rows` и объектом `summary` |
| Выполнение | Анализ пакетов сериализован общей блокировкой модели |

Пустой корректный ZIP возвращает пустой список строк и `summary.status = "empty"`. Ошибки отдельных снимков могут находиться внутри успешного HTTP-ответа: проверяйте `processing_status` и сводку.

| HTTP-код | Значение |
|---|---|
| `200` | Пакет обработан; строки могут содержать ошибки отдельных файлов |
| `400` | Ошибка чтения или подготовки пакета |
| `404` | Неизвестный endpoint |
| `413` | Отсутствующая, нулевая или превышающая лимит длина загрузки |
| `415` | Неподдерживаемый тип содержимого |
| `500` | Необработанная ошибка выполнения на сервере |

### 11.3. API веб-интерфейса

| Запрос | Назначение |
|---|---|
| `POST /api/jobs` | Создание задания; ответ содержит его `id` |
| `PUT /api/jobs/<id>/files?name=<путь>` | Загрузка файла или ZIP в задание |
| `POST /api/jobs/<id>/start` | Запуск анализа |
| `GET /api/jobs/<id>?since=<n>` | Получение состояния и новых строк |
| `GET /api/jobs/<id>/image/<i>` | Получение PNG снимка для просмотра |
| `POST /api/jobs/<id>/items/<i>/rescore` | Пересчёт критериев по изменённым точкам без сохранения решения |
| `POST /api/jobs/<id>/items/<i>/review` | Сохранение решения специалиста и исправленных точек |
| `GET /api/jobs/<id>/report.csv` | Выгрузка CSV |
| `GET /api/jobs/<id>/report.xlsx` | Выгрузка XLSX |
| `GET /api/jobs/<id>/sr.zip` | Выгрузка DICOM SR |
| `GET /api/jobs/<id>/corrections.json` | Выгрузка исправлений специалиста |

Пакетный HTTP API и задания интерфейса используют общую блокировку модели. Запросы к серверу могут обслуживаться в отдельных потоках, однако вычислительный анализ пакетов не выполняется конкурентно.

Сервис предназначен для локальной работы и не содержит собственной аутентификации. При подключении к внешней инфраструктуре необходимы отдельная настройка доступа, аутентификация и reverse proxy.

<a id="operations"></a>

## 12. Обработка ошибок и хранение данных

### 12.1. Файлы и архивы

Каталоги обходятся рекурсивно. Служебные файлы `DICOMDIR`, `.DS_Store`, `Thumbs.db`, `._*`, содержимое `__MACOSX` и документы рядом с исследованиями пропускаются. Число таких объектов отражается в `skipped_non_dicom`.

Для архивов поддерживаются вложенные ZIP до двух уровней, пути Windows с обратными слешами и повторяющиеся имена. При повторе имени добавляется суффикс вида `__dup2`.

Защита распаковки отклоняет элементы с переходом `../`, абсолютными путями, обозначением диска, символическими ссылками, шифрованием или размером более 512 MiB. Такие элементы отражаются в отчёте с причиной ошибки. Пакет отклоняется целиком при превышении ограничений на число файлов, суммарный распакованный объём или при нехватке места.

В релизе заданы ограничения: 200 000 файлов, 64 GiB распакованных данных, до 4096 пикселей по стороне DICOM и до 25 миллионов декодированных отсчётов. Временное пространство контейнера может закончиться раньше общего лимита архива.

### 12.2. Поведение при ошибках

| Ситуация | Результат |
|---|---|
| Пустой, повреждённый или не-DICOM файл, отсутствие PixelData | Строка `Failure`; остальной пакет обрабатывается |
| Константное изображение | `Failure` с сообщением о пустом кадре |
| Неподдерживаемая анатомическая область | `Failure` по результату фильтра вида |
| Многокадровый DICOM | Анализ первого кадра с предупреждением |
| Отсутствующие UID | Детерминированные технические идентификаторы `2.25.*` |
| Отсутствующие или повреждённые веса | Ошибка запуска; проверка через `doctor` |
| Некорректная строка результата, например NaN или неизвестный код | Преобразование проблемной строки в корректную `Failure` |
| Ошибка формирования SR или наложения | Основная строка сохраняется; ошибка отражается в логе и сводке |
| Прерывание пользователем | Код 130; частичный табличный отчёт не записывается |

CSV и XLSX записываются атомарно. Текстовые ячейки XLSX сохраняются как данные. Для CSV исходные строки сохраняются; способ их интерпретации определяется приложением, в котором открывается файл.

### 12.3. Коды завершения CLI

| Код | Значение |
|---|---|
| `0` | Отчёт записан; отдельные строки могут иметь статус `Failure` |
| `2` | Ошибка конфигурации или пакета |
| `3` | Есть `Failure` при включённом `--fail-on-error`; отчёт сохранён |
| `4` | Пустой вход |
| `130` | Прерывание пользователем |

### 12.4. Работа с данными

Пакетный контейнер получает вход только для чтения и работает без сети. Веб-интерфейс обращается к локальному серверу; загруженные файлы удаляются при его остановке. Шрифты и статические ресурсы включены в поставку.

PatientName и PatientID не экспортируются в табличный отчёт. Пути к файлам и идентификаторы исследования и изображения сохраняются в соответствии с форматом задачи. Отчёты, выгруженные пользователем, остаются в выбранном выходном каталоге.

Недостающие UID заменяются техническими детерминированными идентификаторами: по пикселям для изображения и по логической папке для исследования. Эти значения обеспечивают воспроизводимость обработки, но не восстанавливают исходные UID.

## 13. Оценка качества и производительности

### 13.1. Данные и протокол оценки

Оценка выполнена на 249 размеченных снимках: 99 изображениях позвоночника и 150 изображениях бедра, объединённых в 100 исследований. Используются пять фолдов с разбиением по исследованиям.

Каждый обучаемый уровень, голова и порог оцениваются во внешнем фолде, который не участвовал в их обучении. Для CNN бедра использованы вложенные обучения. Доверительные интервалы рассчитаны бутстрэпом по исследованиям.

Метрики ниже соответствуют логике релиза с 18 октября 2026 года, включающей правило рамки ROI.

| Срез | Снимков / нарушений | Чувствительность | Специфичность | Сбалансированная точность | F1 | ROC-AUC |
|---|---|---|---|---|---|---|
| Все области | 249 / 73 | 0.767 [0.64–0.88] | 0.812 [0.74–0.88] | 0.790 [0.72–0.86] | **0.691 [0.58–0.78]** | **0.837 [0.77–0.90]** |
| Позвоночник | 99 / 32 | 0.719 [0.56–0.87] | 0.851 [0.77–0.93] | 0.785 [0.69–0.87] | 0.708 [0.58–0.82] | 0.810 [0.70–0.91] |
| Бедро | 150 / 41 | 0.805 [0.64–0.94] | 0.789 [0.70–0.88] | 0.797 [0.71–0.88] | 0.680 [0.54–0.79] | 0.854 [0.78–0.92] |

Для отдельных причин:

| Причина | Положительных случаев | F1 | ROC-AUC |
|---|---|---|---|
| `spine_scan_range` | 6 | 0.429 | 0.876 |
| `spine_axis_tilt` | 10 | 0.480 | 0.843 |
| `spine_artifact` | 17 | 0.774 | 0.836 |
| `hip_positioning` | 36 | 0.607 | 0.827 |
| `hip_roi_margins` | 7 | 0.727 | 0.827 |

Macro-F1 пяти причин — 0.603 [0.43–0.71]. Полные интервалы и PR-AUC представлены в [METRICS_BY_TYPE.md](METRICS_BY_TYPE.md).

Результаты относятся к выборке разработки одного источника. Правило ROI найдено на этой же выборке: прирост относительно прежнего релиза составил +0.016 F1 и +0.009 ROC-AUC, но интервалы прироста касаются нуля. По принятому протоколу преимущество не считается доказанным; независимая проверка этого изменения отсутствует.

В этих условиях время укладывается в лимит ТЗ 3 минуты на исследование. Воспроизводящий скрипт — [bench_cpu.py](../scripts/bench_cpu.py), описание запуска — [.github/workflows/bench-x86.yml](../.github/workflows/bench-x86.yml).

### 13.3. Проверки релиза

В README зафиксированы следующие результаты проверок команды:

- 499 из 499 DICOM из обучающего архива организатора обработаны со статусом `Success`; таблица разметки пропущена как документ.
- Три снимка тестового архива успешно обработаны образом из комплекта поставки.
- В «грязном» архиве проверены вложенные ZIP, пути Windows, кириллица, повторяющиеся имена, документы, повреждённые и пустые файлы.
- Два прогона на 305 снимках дали одинаковый табличный результат, кроме времени.
- Проверены повороты, сдвиги и изменение контраста; зафиксирован дрейф наклона не более 0,9° и изменение 1–5% решений.

Это результаты, описанные авторами релиза. Они не заменяют независимую оценку на закрытом тесте организатора.

## 14. Эксперименты и воспроизводимость

Выбор модели основан на сравнении вариантов при разбиении по исследованиям. Для оценки прироста применялся парный бутстрэп. Изменение принималось при доверительном интервале прироста целиком выше нуля; для нескольких проверяемых вариантов использовалась поправка Бонферрони.

Основные результаты исследования:

| Направление | Результат и решение |
|---|---|
| Слабая анатомическая разметка GE Lunar из Arak | Улучшила поиск ориентиров; используется в релизе |
| Детектор малого вертела | Детерминированный вариант оказался предпочтительнее обучаемого; используется в релизе |
| Детекторы проволоки и металла | Дали лучшие результаты, чем проверявшийся сегментатор на синтетике; используются в релизе |
| Правило рамки ROI | Добавлено в релиз с 18 октября; независимое подтверждение прироста отсутствует |
| Увеличение CNN, ансамбли, функции потерь и варианты порогов | Устойчивое улучшение по принятому протоколу не подтверждено |
| Самообучение DINO, DINOv2 и RAD-DINO | Проверялись в экспериментах; в выбранный runtime не включены |
| Новые модели A–D и вырез малого вертела | Получены отдельные улучшения ранжирования, но итоговый прирост не прошёл критерии принятия и повторную проверку |
| GCE и ASL для CNN бедра | Эксперимент остановлен до получения результатов |

Полная таблица экспериментов и анализ ошибок находятся в [README](../README.md). Процедура обучения — в [TRAINING.md](TRAINING.md), результаты по причинам — в [METRICS_BY_TYPE.md](METRICS_BY_TYPE.md). Предрегистрации: [новые модели](PREREG_NEW_MODELS.md), [повторная проверка модели C](PREREG_C_CONFIRM.md), [функции потерь CNN бедра](PREREG_HIP_LOSS.md).

Для воспроизведения оценки используются `scripts/run_hip_nested_local.sh`, `scripts/evaluate_final_isolated.py`, `scripts/combine_isolated.py` и `scripts/per_type_metrics.py`. Для их выполнения нужны соответствующие данные и артефакты обучения.

Автоматические проверки запускаются из подготовленного окружения:

~~~sh
.venv/bin/python -m unittest discover -s tests -v
~~~

README описывает 91 тест; три проверки требуют артефактов обучения и пропускаются при их отсутствии. Проверка [test_isolated_folds.py](../tests/test_isolated_folds.py) контролирует, что перестановка меток внешнего тестового фолда не меняет его оценки модели.

## 15. Ограничения и связанные материалы

Система рассчитана на GE Lunar-подобные снимки поясничного отдела L1–L4 и проксимального отдела бедра. Другие области отсекаются фильтром вида. Результаты на другом оборудовании, протоколах и источниках данных требуют отдельной проверки.

Оценочная выборка небольшая и многократно использовалась при разработке. Для редких причин, включая поля ROI и границы сканирования, доверительные интервалы широкие. Небольшие изменения метрик не следует интерпретировать как подтверждённое улучшение.

Измерения зависят от качества предсказанных ориентиров и масштаба изображения. Исправление специалистом предусмотрено как часть рабочего процесса. Программа помогает проводить контроль качества; окончательное решение остаётся за специалистом.

Происхождение весов, внешних данных и компонентов описано в [THIRD_PARTY.md](THIRD_PARTY.md). Условия использования данных и производных весов необходимо учитывать при дальнейшем внедрении.
