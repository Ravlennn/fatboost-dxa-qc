# Метрики по типам нарушений и разбор решений

Ответ на две рекомендации организаторов после созвона 16.10: показать метрики для каждого типа нарушения и объяснить на кейсах, как модель принимает решение.

## Как получены числа

- **Данные:** 249 размеченных снимков (99 позвоночник, 150 бедро) из 100 исследований, 5 фолдов по исследованиям; те же фолды, что в разделе «Метрики» README.
- **Изоляция:** каждый уровень переобучается внутри внешнего фолда; для бедра 25 вложенных обучений CNN. Ни одна модель, голова или порог не видели снимок, на котором их оценивают.
- **Какие решения:** таблицы посчитаны на опубликованных изолированных решениях — тех же, что в таблице README (`decisions_isolated.csv` для позвоночника и `decisions_hip_nested.csv` для бедра, сведённые `combine_isolated.py`); без правил они воспроизводят README до третьего знака (F1 качества 0.675, ROC-AUC 0.828). Полный перезапуск протокола 17.10 на Apple M4 дал для бедра немного другие числа (вложенные CNN на M4 не воспроизводятся бит в бит: ROC-AUC 0.834 против 0.828), поэтому для документа он не используется.
- **Логика релиза** применена к изолированным оценкам в порядке `release_predictor.py`: сначала правило рамки полей бедра, затем «ближайшая причина» (`scripts/per_type_metrics.py`).
- **95% ДИ:** bootstrap по исследованиям, 2000 повторов (`evaluate_final.with_ci`).
- **Это оценка на выборке разработки, а не независимый тест.** У трёх типов 6–10 нарушений, поэтому интервалы F1 широкие.

## Что дало каждое правило

| Логика | F1 качества | ROC-AUC качества | F1 бедра | F1 позиционирования | F1 полей | Средний F1 типов | Брак без причины |
|---|---|---|---|---|---|---|---|
| Только модели (`combined_table.md`) | 0.675 | 0.828 | 0.653 | 0.595 | 0.190 | 0.494 | 12.6% |
| + ближайшая причина (релиз до 18.10) | 0.675 | 0.828 | 0.653 | 0.612 | 0.190 | 0.497 | 0% |
| + рамка за краем снимка (релиз с 18.10) | **0.691** | **0.837** | **0.680** | 0.607 | **0.727** | **0.603** | 0% |

Прирост от правила рамки (парный бутстрэп по исследованиям, 4000 повторов): ΔF1 качества +0.016 [+0.000; +0.041], ΔROC-AUC +0.009 [+0.000; +0.029]. Правило не дало ни одного ложного срабатывания, поэтому нижняя граница — ровно ноль; по протоколу команды (интервал целиком выше нуля) прирост не доказан.

**Правило рамки.** По ТЗ вокруг области интереса бедра нужно поле 3 см сверху и снизу и 2 см по бокам. Если рамка области интереса выходит за край снимка, критерий нарушен при любом понимании рамки. На практике сработать может только нижний или правый край: точки ориентиров — центры ячеек тепловой карты, а при letterbox поля добавляются только снизу и справа, поэтому за кадр точка уходит только там (на валидации поле сверху не меньше 7 мм, слева не меньше 4 мм). В релизе обученная голова полей заменена этим правилом (`roi_edge_score` в `release_predictor.py`), и такой снимок получает брак, даже если общая голова качества сказала «норма».

- Из 7 нарушений полей в разметке у 4 рамка уходит за нижний край: поле −1, −12, −17, −30 мм. У 143 снимков без этого нарушения отрицательных полей нет, наименьшее 0.2 мм.
- Обученная голова срабатывала 14 раз, из них верно 2. В части фолдов её порог был почти нулевым: отношение оценки к порогу доходило до 258.
- Правило на этой выборке дало 4 верных срабатывания и 0 ложных. Два из них — браковые снимки бедра, которые раньше пропускались целиком; отсюда рост F1 качества бедра с 0.653 до 0.680. Побочный эффект: принудительный брак открывает и коды, которые обычная голова скрыла бы, — по ротации это 3 лишние тревоги (F1 0.612 → 0.607).
- **Оговорка:** правило найдено после просмотра этих 7 снимков. Оно не подбирает ни одного параметра (порог — край снимка) и прямо следует из ТЗ, но независимой проверки нет. Отрицательные поля модель ориентиров достраивает за краем кадра; на другом кадрировании это стоит перепроверить. Оставшиеся 3 пропуска — снимки с полями 11–64 мм, их не объясняет ни ТЗ, ни измерения.

## Вероятность каждого типа в отчёте

`dxaqc ... --type-probs` добавляет колонки `prob_spine_scan_range`, `prob_spine_axis_tilt`, `prob_spine_artifact`, `prob_hip_positioning`, `prob_hip_roi_margins`. Они в той же шкале, что `quality_prob`: 0.5 — порог этой причины, значение ≥ 0.5 тогда и только тогда, когда код есть в `violation_type`. Колонки другой области пустые. По ним ROC-AUC можно посчитать отдельно для каждого типа. По умолчанию отчёт прежний: 8 колонок ТЗ и `quality_prob`.

## Как модель принимает решение

Снимок проходит три шага. Для каждого типа нарушения решение опирается на измеримые критерии ТЗ:

| Тип | На чём основано решение | Что видно на наложении |
|---|---|---|
| Границы сканирования | поля над L1 и под L4 в высотах позвонка, видимость гребней подвздошных костей | границы L1–L4 и поля |
| Наклон оси | угол прямой через центры L1–L4, отклонение от прямой | ось позвоночника с углом |
| Посторонние предметы | детектор проволоки и металла вдоль позвоночника вместе с CNN | маска найденных предметов |
| Позиционирование бедра | выступ малого вертела в мм (ТЗ: вертел слегка деформирует контур) вместе с CNN | контур и выступ вертела |
| Поля области интереса | расстояние от рамки области интереса до краёв снимка | рамка и поля в мм |

Карточки решений строит `scripts/make_case_cards.py` → `outputs/case_cards/cases.html`. Отбор механический: на каждый тип верно найденный брак с наибольшей оценкой, пропуск с наименьшей, ложная тревога с наибольшей; верная норма для каждой области. В карточке: снимок с ориентирами, мнение эксперта и его комментарий, решение изолированной валидации с оценкой каждой причины относительно порога, измерения в терминах ТЗ и, отдельно, вердикт финальной модели. Внутри снимки организатора, поэтому файл только локальный.

## Что показали кейсы

Кейсы отобраны на полном перезапуске 17.10; позвоночник в нём совпадает с опубликованными решениями, у бедра номера снимков в отборе могут отличаться.

- **Сколиоз даёт ложный наклон оси.** На снимке со сколиозом прямая через L1–L4 наклонена на 7.1°, модель ставит нарушение оси, эксперт — норму. В разметке 14 снимков позвоночника со сколиозом: 11 норма, 3 брак, и ни у одного нет отметки наклона.
- **Пропуск наклона при угле −1.3°.** Эксперт отметил наклон, хотя по ТЗ нарушение — отклонение более 5°. Это одно из расхождений угла и разметки, о которых мы спрашивали организаторов.
- **Поле над L1 ненадёжно.** При обрезанном кадре модель ориентиров может поставить L1 на другой позвонок, и малое верхнее поле выглядит нормальным (ограничение описано в `run_landmark_fusion.py`). Вероятно, так пропущен один брак границ сканирования: голова дала 0.23 от порога; визуально не проверено.
- **Артефакт не распознан.** В пропуске детектор нашёл только металлическое пятно 7 пикселей, оценка артефакта 0.24 от порога. Брак снимка всё равно выставлен, по наклону оси.
- **Ротация бедра.** И ложная тревога, и пропуск лежат на границе «вертел слегка деформирует контур»: выступ 7.8 мм эксперт считает нормой, 1.8 мм — нарушением. Ротация и позиционирование в разметке одной колонкой, а критерий в ТЗ качественный, без числа.
